monoBERT and duoBERT Multi-Stage Document Ranking

Architectures AIMech:DuoBERTMultiStageDocumentRankingWithBERT DRAFT
Aliases: duoBERT, monoBERT and duoBERT, Multi-Stage Document Ranking with BERT
A three-stage cascading document ranking architecture (H_0 -> H_1 -> H_2) in which a bag-of-words BM25 stage H_0 retrieves top-k_0 candidates R_0 from an inverted index, a pointwise BERT binary relevance classifier stage H_1 (monoBERT) scores each (q, d_i) pair independently via [CLS] cross-entropy classification to retain the top-k_1 <= k_0 candidates R_1, and a pairwise BERT stage H_2 (duoBERT) jointly encodes triples (query q as sentence A, candidate d_i as sentence B, candidate d_j as sentence C with three distinct segment embeddings) to predict the probability p_{i,j} that d_i is more relevant than d_j across all k_1(k_1 - 1) ordered pairs, aggregating the pairwise probabilities via SUM or Condorcet BINARY voting to produce the final ranking R_2.
Identity Notes & Concept Scope Distinct from listwise cross-encoder fusion architectures such as HLATR (AIMech:HLATRHybridListAwareTransformerReranking), which model cross-document interactions over pre-computed pointwise [CLS] vectors in a single listwise Transformer pass rather than running k_1(k_1 - 1) full BERT forward passes over concatenated (q, d_i, d_j) token triples; and distinct from CEDR (AIMech:CEDRContextualizedEmbeddingsForDocumentRanking), which is a single-stage pointwise re-ranker fusing multi-layer token similarity matrices with [CLS].

Mechanism #duobert-three-segment-pairwise-bert-classification-and-loss
Following stage H_0 (BM25 retrieving k_0 candidates R_0) and stage H_1 (monoBERT scoring [CLS] q [SEP] d_i [SEP] trained with pointwise cross-entropy loss L_mono = -sum_{j in J_pos} log(s_j) - sum_{j in J_neg} log(1 - s_j), Equation 1, to select top-k_1 candidates R_1), stage H_2 (duoBERT) takes query q as sentence A (truncated to 62 tokens), candidate d_i as sentence B (223 tokens), and candidate d_j as sentence C (223 tokens)—each with its own learned segment type embedding A, B, C so total length <= 512—and projects the [CLS] vector to pairwise preference probability p_{i,j} trained via L_duo = -sum_{i in J_pos, j in J_neg} log(p_{i,j}) - sum_{i in J_neg, j in J_pos} log(1 - p_{i,j}) (Section 3.3, Equation 2).

Mechanism #duobert-pairwise-probability-aggregation-operators
At inference time, duoBERT evaluates k_1(k_1 - 1) ordered candidate pairs in R_1 and aggregates p_{i,j} over competitor set J_i = {0 <= j < |R_1|, j != i} into a per-document score s_i via SUM (s_i = sum_{j in J_i} p_{i,j}, Equation 3), Condorcet-inspired BINARY (s_i = sum_{j in J_i} 1_{p_{i,j} > 0.5}, Equation 4), MIN (Equation 5), MAX (Equation 6), or m-sample SAMPLE (Equation 7), where SUM and BINARY consistently achieve the highest effectiveness while MAX severely degrades monoBERT accuracy (Section 3.3 & Section 5, Tables 1-2).

  • supports Source: Multi-Stage Document Ranking with BERT · Locator: aggregate_duobert_scores() and main() verification of SUM/BINARY/MIN vs MAX failure
Application #duobert-msmarco-and-treccar-cascading-ranking-application
On MS MARCO passage ranking and TREC 2017 CAR, the BM25 (k_0 = 1000) -> monoBERT (k_1 = 50) -> duoBERT pipeline improves MS MARCO Dev / Eval MRR@10 from 18.7 / 19.0 (BM25) to 37.2 / 36.5 (+monoBERT), 38.2 / 37.0 (+duoBERT_SUM), 38.3 Dev (+duoBERT_BINARY), and 39.0 / 37.9 with Target Corpus Pre-training (TCP, Table 1), while on TREC CAR it raises MAP from 15.3 (BM25) to 34.8 (+monoBERT) and 36.9 (+duoBERT_SUM or duoBERT_BINARY, Table 2), with k_1 = 20 capturing nearly the full gain at only 40% extra latency over monoBERT (Section 5.2, Figure 3).
  • supports Source: Multi-Stage Document Ranking with BERT · Locator: Section 5, Tables 1-3 & Figures 2-4, pp. 6-10
Limitation #duobert-quadratic-pairwise-inference-cost-and-length-truncation-limitation
Because duoBERT executes k_1(k_1 - 1) full BERT forward passes per query (e.g., 50 x 49 = 2,450 additional BERT inferences on top of k_0 = 1000 monoBERT inferences, totaling 3,450 BERT passes per query at k_1 = 50), inference cost grows quadratically in k_1 (Sections 3.3 & 5.2, Figures 3-4), and fitting two candidate documents alongside the query within BERT's 512-token window requires truncating each candidate to at most 223 tokens (Section 3.3).
  • supports Source: Multi-Stage Document Ranking with BERT · Locator: Section 3.3 & Sections 5.2-5.3, Figures 3-4, pp. 4, 7-9

⚠️ Curated Limitations & Negative Results

  • Requires k_1(k_1 - 1) pairwise BERT forward passes per query in stage H_2 (e.g., 2,450 extra BERT inferences for k_1 = 50), causing latency to scale quadratically with candidate pool size k_1.
  • Concatenating the query and two candidate documents into a single 512-token BERT input restricts each candidate document to at most 223 tokens.
