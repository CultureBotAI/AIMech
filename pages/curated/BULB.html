Beam search using limited discrepancy backtracking

Aliases: BULB, Limited discrepancy beam search
A memory-bounded beam search that explores heuristic-ranked slices using increasing limited-discrepancy budgets and removes backtracked slices so that alternative beams can be examined.
Definition Evidence
  • supports Source: Limited Discrepancy Beam Search · Locator: Sections 2–3.3, PDF pp. 2–4; Figure 4 on PDF p. 3
Identity Notes & Concept Scope BULB denotes Furcy and Koenig’s Beam search Using Limited discrepancy Backtracking. A discrepancy selects a nonpreferred successor slice; it is not a numerical heuristic error or an action cost. The inspected algorithm is presented for unit-cost state-space search and seeks a path, not necessarily a shortest path. No normalized identity match was found across the 442 AIO and 130 prior native records; ignored-inclusive text hits in the main checkout were prior discovery leads, source citations and search-order contrasts, plus incidental lightbulb and wet-bulb dependency substrings, not existing concept records.

Claims & Grounded Evidence

3 Claims
Mechanism #search-procedure
Keep one slice of up to the beam width at each active depth. Rank eligible successors by heuristic value and divide them into slices. A probe follows the preferred slice without spending discrepancy allowance and explores nonpreferred slices with a reduced allowance, removing slices from the active hash table on backtracking. Outer iterations increase the allowance; a full table causes the current probe to stop and backtrack.
  • supports Source: Limited Discrepancy Beam Search · Locator: Sections 2–3.3, PDF pp. 2–4; Figure 4 on PDF p. 3
Limitation #memory-qualified-completeness
The paper qualifies completeness by the memory needed to retain a beam to a solution and describes the base method as approximate in solution length. Its conclusion discusses conversion to an anytime algorithm as an extension, not an automatic guarantee of the presented stopping rule.
  • supports Source: Limited Discrepancy Beam Search · Locator: Section 3.4, PDF p. 4; Conclusion, PDF p. 7
Limitation #depth-label-inconsistency
Visual inspection identifies an apparent inconsistency between the recursive depth increment and the depth label assigned to generated successors. The next-level interpretation comes from the adjacent prose; no corrected reference implementation or author erratum was established by this review.
  • supports Source: Limited Discrepancy Beam Search · Locator: Figure 4, PDF p. 3: recursive depth increment and nextSlice depth assignment; Section 3.3 prose, PDF p. 4

⚠️ Curated Limitations & Negative Results

  • Completeness is conditional on enough memory to store a beam along a solution path. A fixed memory budget and arbitrary beam width do not guarantee solving every instance.
  • The method need not return a shortest path. An anytime extension is discussed separately from the base procedure.
  • The O(B*d) storage statement concerns retained slices along the active search; temporary successor generation, heuristic data and other implementation storage need separate accounting.
  • The active hash table prevents cycles involving retained states and some transpositions, but it is not a permanent global closed list of every state ever visited.
  • Figure 4 has an apparent depth-label inconsistency: nextSlice labels a successor with depth although the caller next probes depth+1. The prose describes a next-level slice. This record follows that described mechanism and does not certify the literal pseudocode as executable.
