Iterative threshold search

Algorithms AIMech:IterativeThresholdSearch DRAFT
A limited-memory heuristic tree-search algorithm that explores branches within an iteratively revised cost threshold, stores bounds for branches whose children may still be ungenerated, and backs up those bounds when retracting stored nodes.
Identity Notes & Concept Scope Iterative threshold search denotes the limited-memory tree procedure of Ghosh, Mahanti and Nau (1994), which combines cost-threshold passes with per-branch bounds including ungenerated successors, retraction and retained lower-bound information. It is distinct from ordinary smallest-excess IDA*, learned threshold-prediction IDA*IM, MREC, RBFS and beam search. The ambiguous bare acronym ITS is not added as an alias. The literal Background h(n)>0 versus Example 1 h(n)=0 discrepancy is retained. The two-tip retraction guard preserves the current path, so S=0 does not imply zero total storage. Claims & Grounded Evidence

4 Claims
Mechanism #branch-state-before-child-generation
When installing a node, ITS creates a branch for each applicable operator without needing to invoke that operator to generate its child. Each branch bound B starts at the installed node’s g + h; a dummy branch is installed when no operator applies.
  • supports Source: ITS: An Efficient Limited-Memory Heuristic Tree Search Algorithm · Locator: Algorithm ITS, printed pp. 1353–1354 / PDF pp. 1–2; branch representation and Install procedure
Mechanism #threshold-and-leftmost-selection
Each outer iteration sets the threshold to the minimum bound among tip branches. ITS repeatedly selects the leftmost tip branch whose bound does not exceed that threshold, tests its parent node for a goal, and either handles a dummy branch or installs the selected child.
  • supports Source: ITS: An Efficient Limited-Memory Heuristic Tree Search Algorithm · Locator: Printed p. 1354 / PDF p. 2; Procedure ITS, steps 2(a)–2(b)iii
Mechanism #retraction-and-bound-backup
Before installing a child, if the stored tree has at least S nodes and at least two tip nodes, ITS retracts the leftmost tip node whose outgoing branch bounds all exceed the threshold, or otherwise the rightmost tip node. It places the minimum outgoing bound on the retracted node’s incoming branch and removes the node and its outgoing branches.
  • supports Source: ITS: An Efficient Limited-Memory Heuristic Tree Search Algorithm · Locator: Printed p. 1354 / PDF p. 2; Procedure ITS, step 2(b)iiiA and definitions of tip node and retraction
Scope #minimum-storage-keeps-active-path
S controls the amount of node storage used by the retraction condition. In the S = 0 setting described in the experiments, ITS retains the current search path while retracting other nodes; per-branch bounds and operator information still have to be represented.
  • supports Source: ITS: An Efficient Limited-Memory Heuristic Tree Search Algorithm · Locator: Printed pp. 1354–1355 / PDF pp. 2–3; storage definition, two-tip retraction guard and Experimental Results memory-setting paragraph

⚠️ Curated Limitations & Negative Results

  • S counts nodes in the algorithmic storage model, not bytes, and the two-tip-node retraction guard preserves the current path. S = 0 therefore does not mean zero memory or a strict zero-node cap; branch bounds and operator bookkeeping also consume storage.
  • The Background prints h(n) > 0 and admissibility h(n) <= h*(n), whereas Example 1 sets h(n) = 0 for every node. This record preserves that source discrepancy rather than silently changing the strict inequality. Under a nonnegative admissible interpretation with zero remaining cost at a goal, h(goal) = 0 follows; that is a conditional interpretation, not a consequence of the literal strict-positive display.
  • Theorem 2 states termination with an optimal solution, while the paper refers its proofs to Ghosh’s 1994 thesis, which has not been inspected. This record does not certify unrestricted termination for unsolvable or infinite instances, zero-cost cycles or arbitrary negative costs, and does not attribute unprinted finite-contour or positive-cost premises to that theorem.
  • ITS maintains a search tree even when the underlying problem is described as a directed state graph. The inspected pseudocode does not specify a general graph transposition table or closed-list/reopening mechanism.
  • Theorem 4’s node-generation comparison with IDA* requires the same left-to-right sequence of operators. Its generation counts are not a universal wall-clock-runtime comparison, and changing ordering can fall outside that statement.
  • The paper’s constructed asymptotic example is a particular family of finite binary trees. Its sampled traveling-salesman results and optimality suggestion do not prove average-case or asymptotic optimality across arbitrary problem distributions.
  • The modified ITS-prime(0) used for the flow-shop comparison in Table 1 is distinct from standard ITS(0) in Table 2. Results for that modification are not silently attributed to the standard ITS algorithm.
  • Runtime depends on bookkeeping and node-generation cost; fewer generated nodes do not imply a faster implementation. The 15-puzzle discussion also warns that the two largest reported cases were affected by counter overflow and possible thrashing, so those results are not clean general performance evidence.
